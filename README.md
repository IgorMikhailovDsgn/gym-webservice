# GymManager

Веб-приложение для управления фитнес-центром: учёт клиентов, абонементов
и посещений.

Стек:
- ASP.NET Core Web API 10.0
- PostgreSQL 18 · EF Core (Db-First)
- React 18 · TypeScript · Vite · Ant Design


## Запуск

### 1. База данных

```bash
cd db
docker compose up -d
docker compose logs -f db     # ждём "database system is ready to accept connections"
```

Схема и тестовые данные применяются автоматически при первой инициализации
тома. Проверка:

```bash
docker compose exec db psql -U gym -d gym -c "SELECT count(*) FROM clients;"
```
Ожидается 50.

> **Переинициализация.** Чтобы применить изменения схемы заново:
> `docker compose down -v && docker compose up -d`

### 2. Бэкенд

```bash
cd backend
dotnet restore
dotnet run --project src/GymManager.Api
```

API поднимется на `http://localhost:5080`.
Swagger: `http://localhost:5080/swagger`

### 3. Фронтенд

```bash
cd frontend
npm install (если нет node, то сначала brew install node)
npm run dev
```

Интерфейс: `http://localhost:5173`

## Архитектурные решения

Диаграммы модели данных и основных сценариев — в [diagrams.md](diagrams.md).

### Слоистая архитектура с инверсией зависимостей

Три проекта на бэкенде, зависимости направлены так:

```
Api ──────────► Application ◄────── Infrastructure
 └──────────────────────────────────────┘
        (только регистрация в DI)
```

`Application` не ссылается ни на один проект и не содержит пакетов EF или
ASP.NET. Интерфейсы репозиториев объявлены **в ней**, а реализованы
в `Infrastructure` — интерфейс принадлежит тому, кто им пользуется.

Практическое следствие: бизнес-логику можно тестировать без базы, подставив
фейковый репозиторий, а замена СУБД или способа доставки (REST → gRPC)
не затрагивает середину.

Это **модульный монолит**: один процесс, одна БД.
Разделение фронта и бэка — клиент-серверная архитектура

### Статус абонемента вычисляется, а не хранится

Ключевое решение проекта.

Статус зависит от текущей даты: абонемент, истекающий 25 августа, в ночь
на 26-е должен стать просроченным — но никакой операции записи при этом
не происходит. Хранимое поле неизбежно устаревает.

PostgreSQL это подтверждает: генерируемая колонка требует IMMUTABLE-выражения,
а `CURRENT_DATE` таковым не является. Статус физически невозможно сохранить
корректно.

Решение — представление `v_tickets` с `CASE`:

| Статус | Условие |
|---|---|
| `cancelled` | установлен флаг ручной отмены |
| `pending` | дата начала ещё не наступила |
| `expired` | дата окончания прошла |
| `exhausted` | лимит посещений выбран |
| `active` | остальное |

Хранится только `is_cancelled` — это **событие** (кто-то принял решение),
а не следствие. Общее правило: события хранятся, следствия вычисляются.

Побочная выгода: фильтровать по статусу можно средствами SQL с пагинацией.
Будь статус в C#, пришлось бы грузить все абонементы в память.

Альтернатива с materialized view отвергнута: она требует явного `REFRESH`
и возвращает ту же проблему устаревания.

### Условия абонемента копируются из справочника

`ticket_types` — шаблон. При оформлении срок и лимит **копируются**
в `tickets`, а не читаются по ссылке.

Иначе правка «месячный теперь 10 занятий вместо 8» задним числом изменила бы
условия всех проданных абонементов, включая закрытые.

Второе следствие: `CHECK (visits_used <= visits_limit)` возможен только
потому, что лимит лежит в той же строке — CHECK не умеет подзапросов.

### `NULL` означает «без ограничения»

`visits_limit IS NULL` — безлимитный абонемент. Соглашение проходит через
всю систему: схему, CHECK-ограничения, представление, C#-модели и TypeScript.

### Фиксация посещения: транзакция с блокировкой строки

Операция изменяет две вещи — вставляет строку в `visits` и увеличивает
`visits_used`. Между чтением и записью происходит проверка правил.

Без блокировки два одновременных запроса по абонементу с одним оставшимся
посещением оба прошли бы проверку и списали два. Поэтому абонемент читается
через `SELECT ... FOR UPDATE`: второй запрос ждёт завершения первого.

Последний рубеж — `CHECK` на уровне БД: даже при баге в приложении лимит
превысить нельзя.

### Валидация в трёх слоях

| Уровень | Что проверяет | Ответ |
|---|---|---|
| FluentValidation | формат: обязательность, длина, шаблон | 400 |
| Сервис | бизнес-правила | 409 с кодом причины |
| CHECK в БД | инварианты целостности | защита от багов |

Дублирование намеренное: база даёт гарантию, приложение — понятное сообщение.

### Обработка ошибок

Единая middleware превращает исключения в ответы формата ProblemDetails
(RFC 7807). Контроллеры не содержат `try/catch`, сервисы не знают про HTTP.

`BusinessRuleException` несёт машиночитаемый `code` (`ticket_expired`,
`ticket_exhausted`), чтобы фронт мог реагировать по-разному, не разбирая текст.

### Db-First и защита ручных правок

Схема в `db/01_schema.sql` — единственный источник правды. Модели
генерируются скаффолдингом:

```bash
cd backend
dotnet ef dbcontext scaffold \
  "Host=localhost;Port=5432;Database=gym;Username=gym;Password=gym_local_pwd" \
  Npgsql.EntityFrameworkCore.PostgreSQL \
  --project src/GymManager.Infrastructure \
  --startup-project src/GymManager.Api \
  --context GymDbContext --context-dir Persistence --output-dir Entities \
  --no-onconfiguring --force
```

`--no-onconfiguring` не даёт вшить строку подключения с паролем
в сгенерированный код.

Сгенерированные файлы **правятся только через `partial`**: ручная
конфигурация вынесена в `Persistence/GymDbContext.Configuration.cs`
и переживает пересканирование. Там указано, что `updated_at` заполняется
триггером БД, — из схемы скаффолдер этого узнать не может.

### Поиск по ФИО

GIN-индекс `pg_trgm` строится по склеенным фамилии, имени и отчеству
в нижнем регистре. Запрос в LINQ повторяет это выражение символ в символ —
планировщик использует индекс по выражению только при точном совпадении.

Поэтому «иванов ив» находит «Иванов Иван Петрович», чего не даёт поиск
тремя отдельными `OR` по полям.

### Аутентификация

JWT без ролевой модели. `visits.user_id` берётся **из токена**, а не из тела
запроса: иначе любой мог бы записать посещение от чужого имени.

## Допущения

- **Ролей нет.** Все сотрудники равноправны. Точка расширения — колонка
  `role` в `users` и политики авторизации.
- **Регистрация сотрудников не реализована.** Пользователи заводятся
  сид-скриптом.
- **Удаления нет.** Клиенты и абонементы деактивируются статусом, внешние
  ключи стоят на `ON DELETE RESTRICT`.
- **Посещения неизменяемы.** Строка `visits` не редактируется и не удаляется,
  поэтому у неё нет `updated_at`. Оформление задним числом не поддержано.
- **Одна дата у клиента.** `created_at` играет роль даты регистрации:
  разойтись они могли бы только при импорте из внешней системы.
- **Границы дат включительные.** Абонемент действует по `date_end`
  до конца дня, поэтому тип `date`, а не `timestamp`.
- **Поиск по телефону не реализован** в API (индекс в БД подготовлен).
- **Типы абонементов на фронте захардкожены** — эндпоинта
  `GET /api/ticket-types` нет.
- **Ключ JWT лежит в appsettings** — приемлемо для локального запуска,
  в бою его место в переменных окружения.

## API

Все эндпоинты, кроме входа, требуют заголовок
`Authorization: Bearer {token}`.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/auth/login` | вход, выдача JWT |
| GET | `/api/clients` | список: поиск, фильтр по статусу, пагинация |
| GET | `/api/clients/{id}` | карточка клиента |
| GET | `/api/clients/{id}/tickets` | история абонементов |
| POST | `/api/clients` | создание |
| PUT | `/api/clients/{id}` | редактирование |
| GET | `/api/tickets` | список: фильтр по статусу и дате действия |
| POST | `/api/tickets` | оформление |
| POST | `/api/tickets/{id}/extend` | продление |
| POST | `/api/visits` | фиксация посещения |

### Коды ответов

| Код | Когда |
|---|---|
| 400 | ошибка формата, детали в `errors` |
| 401 | нет токена или он недействителен |
| 404 | объект не найден |
| 409 | нарушено бизнес-правило, причина в `code` |

## Развёртывание

Приложение состоит из трёх частей: PostgreSQL, ASP.NET Core API,
статика фронтенда.

### Подготовка сборок

```bash
cd backend
dotnet publish src/GymManager.Api -c Release -o ./publish

cd ../frontend
npm run build          # результат в dist/
```

Перед сборкой фронта укажи адрес API в `frontend/.env`:

```
VITE_API_URL=https://ваш-домен/api
```

Переменная подставляется **на этапе сборки**, менять её после `npm run build`
бесполезно.

### Настройки для production

Строку подключения и ключ JWT задавать переменными окружения, а не файлом:

```bash
export ConnectionStrings__GymDb="Host=...;Database=gym;Username=...;Password=..."
export Jwt__Key="случайная-строка-не-короче-32-символов"
export ASPNETCORE_ENVIRONMENT=Production
```

Двойное подчёркивание — разделитель уровней вложенности конфигурации .NET.

В `Program.cs` разрешённый источник CORS указан как `http://localhost:5173`.
Для боевого стенда заменить на реальный домен.

Swagger включается только в Development и в production будет недоступен —
это осознанно.

### Схема БД на сервере

```bash
psql -h ХОСТ -U ПОЛЬЗОВАТЕЛЬ -d gym -f db/01_schema.sql
psql -h ХОСТ -U ПОЛЬЗОВАТЕЛЬ -d gym -f db/02_seed.sql   # опционально
```

Сид содержит тестовые данные и пароли по умолчанию — на публичном стенде
его применять не стоит, кроме заведения реального пользователя.

### Обратный прокси

Типовая схема: nginx отдаёт статику фронтенда и проксирует `/api`
на приложение.

```nginx
server {
    listen 80;
    server_name ваш-домен;

    root /var/www/gym/dist;
    index index.html;

    # SPA: любой неизвестный путь отдаём index.html,
    # иначе перезагрузка страницы /clients/{id} даст 404
    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api {
        proxy_pass http://127.0.0.1:5080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

HTTPS-сертификат — через certbot либо средствами панели хостинга.

Приложение удобно держать под systemd, чтобы оно поднималось после
перезагрузки.

## Что реализовано из ТЗ

**Учёт клиентов и абонементов:** список, создание, редактирование, карточка,
оформление абонемента, продление, история абонементов.

**Учёт посещений:** фиксация, история, текущий статус абонемента,
остаток посещений.

**Поиск и фильтрация:** поиск по ФИО, фильтр клиентов по статусу,
фильтр абонементов по сроку, переход к карточке клиента.

**Бизнес-правила:** посещение только по активному абонементу; просроченный
использовать нельзя; лимит не превышается; посещение уменьшает остаток.

**Сверх требований:** пагинация, JWT-аутентификация, ProblemDetails,
Swagger с описаниями, вычисляемые статусы на уровне БД.
